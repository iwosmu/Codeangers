# task_assigner (temporary, not wired into the app yet)

Takes the `team.md` generated by the brief pipeline and the task graph produced by
the task planner (`POST /api/task-graph`, or `python -m app.task_planner`), and asks
Gemini who does which task and in what order. The model works the schedule out
(prerequisites, estimates, head-counts, evidenced skills, whole-team utilisation)
but returns only the assignment: names per task, an ordered task list per member,
and notes for tasks that had to go to someone without evidence for a skill.

```
task_assigner/
  prompts.py      system instruction, assignment prompt, fix-round prompt
  schema.py       ASSIGNMENT_SCHEMA passed as response_json_schema; Member/Task/Assignment types
  team.py         parse_members(): Member IDs and names from team.md
  tasks.py        load_tasks() for every planner output shape; check_tasks(); critical_path_hours()
  validation.py   validate_assignment(): both views agree, exact head-counts, a simulation of
                  the execution rules (deadlocks, idle time), warnings worth sending back
  assigner.py     TaskAssigner: generate -> validate -> send errors back -> repeat
  __main__.py     CLI
tests/            no network; a stubbed client stands in for Gemini
```

## Install

The package only needs `google-genai>=1.0,<3`, which the API's environment already
has. From the repository root, with the API venv created by `uv sync` in `api/`:

```
api\.venv\Scripts\python -m pytest temp -q            # Windows
api/.venv/bin/python -m pytest temp -q                # elsewhere
set GEMINI_API_KEY=...                                # export GEMINI_API_KEY=... elsewhere
```

Standalone: `pip install -r temp/requirements.txt` and run with `temp/` as the
working directory or on `PYTHONPATH`.

## Use

CLI, from `temp/`:

```
python -m task_assigner team.md plan.json -o assignment.json
python -m task_assigner team.md plan.json --show-schedule          # also print the simulated timeline
python -m task_assigner team.md plan.json --allow-invalid          # write even if validation still fails
```

`plan.json` can be anything the planner writes or returns: the flat task list
(`--format tasks` / `data.tasks`), the `{nodes, edges}` graph (the planner CLI's
default) or the whole API envelope. Both files are read as UTF-8. The key comes from
`GEMINI_API_KEY` in the environment, as for the planner CLI.

From code:

```python
from task_assigner import TaskAssigner, AssignerConfig

assigner = TaskAssigner(config=AssignerConfig(model="gemini-3.8-flash", max_fix_rounds=2))
result = assigner.assign(team_md, tasks)         # tasks: planner output in any shape
print(result.validation.summary())
if result.ok:
    result.assignment                            # {"tasks": [...], "people": [...], "notes": [...]}
    result.validation.schedule                   # {task id: (start hour, end hour)} from the local simulation
```

`assign(team_md, tasks, members=[{"id": "m1", "name": "Ala"}, ...])` skips the
`team.md` parsing for a hand-written team document. A `genai.Client` can be injected
with `TaskAssigner(client=...)`.

## Output format

```json
{
  "tasks": [
    {"task_id": 1, "task_name": "Set up repository", "assigned_to": ["Ala"]},
    {"task_id": 7, "task_name": "Integrate API and frontend", "assigned_to": ["Ala", "Bartek"]}
  ],
  "people": [
    {"member_id": "m1", "name": "Ala", "task_ids": [1, 4, 7, 10]},
    {"member_id": "m2", "name": "Bartek", "task_ids": [2, 5, 7, 10]}
  ],
  "notes": [
    {"task_id": 5, "name": "Bartek", "note": "Needs React; nobody has evidence for it. Bartek has the closest background (TypeScript, some frontend coverage) and should read up before starting."}
  ]
}
```

- `tasks`: every task once, with exactly `people_needed` member names, spelled as the
  member headings in `team.md`.
- `people`: every member once, with their task ids in execution order; a member with no
  work has an empty list.
- `notes`: one entry per task assigned under the closest-skills fallback, plus anything
  the model could not satisfy; `task_id` 0 means the note is about a member, not a task.

The execution rules the output is checked against: everyone is available from hour 0,
hours are abstract units; a member starts the next task in their list when their
previous task is finished, every prerequisite is finished and every co-assignee is
free; a multi-member task runs with all its members for its whole duration; the order
of a list is binding.

## How it works

1. `tasks.load_tasks` normalises the planner output and `check_tasks` rejects an
   unusable list (duplicate ids, dangling prerequisites, cycles) before any call.
2. `team.parse_members` reads the Member IDs and names from `team.md`.
3. `prompts.build_user_prompt` embeds both documents; the prompt carries the execution
   rules, hard constraints (fixed task list, evidenced skills only with a
   closest-background fallback, no overlaps, exact head-counts) and the optimisation
   order (project duration, full utilisation, skill fit, balance).
4. `generate_content` runs with `response_json_schema=ASSIGNMENT_SCHEMA`.
5. `validation.validate_assignment` checks that the two views agree, that every task has
   exactly `people_needed` members and every member appears, then simulates the lists
   under the execution rules: a deadlock (lists that can never complete) or an idle
   fraction above `max_idle_fraction` (default 25 %) is an error; idle stretches while
   work was ready, a project longer than its critical path, and names that differ from
   the document are warnings.
6. On errors the model's own turn plus the problems are sent back and a complete
   corrected assignment is requested, up to `max_fix_rounds` times.

## Knobs (`AssignerConfig`)

| field               | default            | note |
|---------------------|--------------------|------|
| `model`             | `gemini-3.8-flash` | any Gemini 3.x / 2.5 model |
| `thinking_level`    | `"high"`           | Gemini 3.x only; scheduling is the hard step, so high; set `None` for 2.5 |
| `thinking_budget`   | `None`             | Gemini 2.5; `-1` = dynamic |
| `max_output_tokens` | `32768`            | includes thinking tokens |
| `temperature`       | `None`             | leave default on Gemini 3 |
| `max_fix_rounds`    | `2`                | correction rounds after the first attempt |
| `max_idle_fraction` | `0.25`             | idle capacity above this is an error |

## Limits

- Skill fit is judged by the model from `team.md`; the validator cannot check it. Read
  the `notes` and the coverage map before trusting a fallback assignment.
- The simulation counts abstract hours and heads only; it does not know that a member
  who learns a skill on the job will be slower than the estimate.
- Names are matched to the `## <name>` headings of `team.md`. Two members with the same
  name are told apart by `member_id` in the `people` view; the tasks view then only
  shows the shared name.
- Expect one to a few minutes per run: the call uses high thinking and up to three
  model calls.
